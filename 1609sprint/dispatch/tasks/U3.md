# U3: build the Production host once for the telemetry phase assertions (PR 764)

## Aim

The six-shard CI run for PR 764 (run 35156082193) passed five shards in 15–20 minutes and timed out
on shard 6 at 45 minutes. The measured cause is `tests/Pegasus.IntegrationTests/ProductionCompositionTests.cs`:
PR 764 turned `ProductionWebTelemetryEmitsAllowlistedDocumentTimingWithRequestCorrelation` from one
`[Fact]` into a 23-row `[Theory]`, and every row builds its own Production
`ConfiguredWebApplicationFactory`, which costs ~90–100 s of startup per row (local TRX at
`artifacts/performance/a13e97373/host-verification-20260916/test-results/03-focused-integration.trx`
shows 21 rows between 57 s and 104 s). xUnit runs a class's tests serially, so the class alone needs
about 35 minutes on whichever shard holds it; it was on the old timing-out shard 2 and on the new
shard 6. Nothing else on shard 6 is slow (the rest of its classes sum to ~54 minutes serial across
four threads).

## Required change

1. In `ProductionCompositionTests.cs` (~line 375): replace the 23-row theory with one `[Fact]` that
   builds the Production factory and the `RecordingTelemetryChannel` **once**, then iterates the same
   23 phase names (keep them as a static readonly array in the test so the allowlist stays explicit),
   and for each phase: starts a fresh `Activity("test.request")`, runs `DocumentReadTelemetry.Start(phase)`,
   and makes exactly the assertions the theory makes today (single matching `EventTelemetry` for that
   request's TraceId/ParentId, `ISupportSampling`, `phase` and `AspNetCoreEnvironment` properties, exactly
   two properties, `durationMs` the only metric and >= 0, operation ids). Use `Assert.Single` over the
   events filtered by that request's operation id so earlier phases' events do not interfere.
   Every assertion and every phase from the current data set must remain; do not drop any phase.
2. Check `ProductionWebTelemetryIncludesPublicUploadUrlSanitization` (~line 338) is a single host
   construction already; leave it.
3. If the ~95 s startup is caused by an outbound wait in Production composition that a test can
   legitimately short-circuit (for example an unreachable endpoint with a 100 s timeout), note the
   cause in your summary but do not change production composition in this task.
4. No change outside that test file (and, if genuinely needed, its test support).
