# Additional-provider activation

Pre-conversion status: **Planned activation contract; no additional-provider caller exists.**

## Scope, ownership and caller

Activate one approved additional provider at a time through the existing provider-neutral intake and case workflow. Core continues to own source-processing/acceptance policy; a contained provider extraction/reference policy may interpret only that provider's approved inputs. Web, Worker, or a provider endpoint is an intended composition-root caller selected by the activation decision, not a new intake engine.

Dependencies are accepted V1 operator/management release evidence, staff identity/action history, configured principal/reference data, durable custody, and the existing intake/acceptance plans. A provider-specific project, allocator, case workflow, generic provider framework, credential, external call, or cloud resource is excluded now.

## Activate an additional provider

Before implementation, obtain a direct provider/product contract for permitted source formats, principal mapping, reference data provenance/effective date, authentication/transport, data handling, error ownership, representative non-corpus evidence, and the exact intended caller. The Core owner must reject incomplete, contradictory, unknown, replayed, or out-of-scope input before case/reference allocation; ambiguous standalone Audit type also remains pre-allocation. No policy may change an allocated principal/reference, and wrong-principal handling remains reasoned `Created in error` plus linked replacement.

Focused tests prove contained extraction decisions and no duplicate allocation; integration and genuine local evidence prove the selected caller, durable source identity, replay/idempotency, action history, and visible operator outcome. A later approved shared-development smoke may prove only its exact provider/account/scope. It does not prove other providers, production, or acceptance.

Roll out behind an explicitly approved provider allowlist after one caller-backed journey and operator review. Recover by disabling that provider route, retaining receipts/evidence and reconciling failures; never delete or reuse allocated identities. Approval is required for the provider contract, data/credential/security scope, external activation, and release. The irreversible choice is any provider-specific data contract or allocated case identity; retain stable source/provider/external identities and reversible mapping evidence, not dormant adapters.

## Deferred-capability impact

This is the activation seam for later providers only. It preserves the single Core intake/acceptance owner and bounded provider policy boundary; it deliberately does not pre-build other provider rules, integrations, schemas, queues, flags, or accounts. Future activation evidence is an accepted provider contract, caller-backed representative proof, security/cost approval, and operator acceptance.
