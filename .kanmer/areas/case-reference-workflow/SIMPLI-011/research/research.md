# Research — SIMPLI-011: decompose the Case Details workspace by capability

## Question

What does `Pages/Cases/Details` own today, what already exists as the "capability-specific Razor endpoint" pattern, what constrains the move (design authority, tests, shared state), and what would a mechanical, behaviour-preserving extraction cost?

## Verified vs assumed

- Verified: everything above by grep/read.
- Assumed (planner decisions in `open-questions`): endpoint shape (one page per family with named handlers, not a dispatching action), a shared base for the mutation pages, `EvaDownload` as its own download page.

## Implications

Because every mutation is already PRG and every form already carries the case id, the extraction is mechanical: each handler becomes an `OnPost<Name>` on its capability page; each form gains one `asp-page`; `Details.cshtml` and the visible workspace do not change. The real cost — and the ticket's second verification line — is **behavioural tests for the 22 uncovered handlers** (~35 lines each in the existing `CaseDetailsWebTests` idiom: GET for antiforgery → `ClaimLease` → POST handler → `AssertPrg` + persisted-state assertion). Without a shared base, ~200 lines of lease/actor/command plumbing would be duplicated five times — the third-copy rule applies.
