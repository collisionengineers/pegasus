# Research — SIMPLI-014: integrate CollisionRenderer behind a Core-owned render contract

## Question

What must move from `workspaces/report-renderer/` into Pegasus, where does each responsibility belong, and what unresolved product decisions prevent a complete, caller-backed assessment-report integration?

## Findings

- The integration direction is binding: CollisionRenderer is part of the Pegasus .NET monolith and existing Azure application, never a separate product, service, API, MCP host, package, repository, or deployment unit. `Pegasus.Core` owns readiness, policy, identity and the render port; Infrastructure adapts the rendering engine; Web/Worker are composition roots. Sources: EPIC-004 `context.md`; `docs/adr/0025-integrate-renderer-and-extractor-into-the-application.md`; AGENTS.md.
- ADR-0025's activation conditions are now met in intent but not in implementation: [[DOCS-001]] supplies the real assessment caller and durable render-result workflow, while [[PLAT-007]] supplies Azure composition and deployment. SIMPLI-014 blocks DOCS-001, which blocks PLAT-007. Sources: SIMPLI-014 links; ticket bodies for DOCS-001 and PLAT-007.
- The existing application has exactly four production projects. Core owns ports/policy, Infrastructure owns external adapters, and Web plus Worker compose them. A new production project or deployable would require an accepted ADR, while the accepted direction says to use the existing topology unless research proves otherwise. Sources: AGENTS.md product invariants; ADR-0002; `Pegasus.slnx`; `tests/Pegasus.ArchitectureTests/DependencyDirectionTests.cs`.
- The renderer workspace has one rendering pipeline, `IDocumentRenderer` → `DocumentRenderer` → `IPdfEngine`, created by `CollisionRendererFactory`. It validates typed payloads, composes Scriban HTML, renders with Playwright Chromium, counts/appends PDFs with PDFsharp, computes SHA-256, and returns PDF bytes, page count, engine/template identity, density, filename and warnings. This is reusable adapter machinery, not Pegasus business policy. Sources: `workspaces/report-renderer/src/CollisionRenderer.Core/Contracts.cs`, `DocumentRenderer.cs`, `CollisionRendererFactory.cs`, `Rendering/PdfEngine.cs`.
- The workspace's current `CollisionRenderer.Core` name is misleading after integration: it contains Scriban, Playwright, PDFsharp, template catalogues and attachment-path policy, all of which are forbidden dependencies/mechanics for `Pegasus.Core`. The engine should be folded into `Pegasus.Infrastructure` behind a small Core-owned report-rendering port rather than added as a fifth production project. Sources: ADR-0002 dependency rules; AGENTS.md one-Core-owner and no-new-project invariant; `CollisionRenderer.Core.csproj`.
- The standalone hosts are not application integration seams. `CollisionRenderer.Api`, `CollisionRenderer.Cli`, and `CollisionRenderer.Mcp` translate transports to the same engine, but Pegasus already owns HTTP/MCP in Web and durable background work in Worker. The API and standalone MCP host must not enter the application deployment; any retained developer-only CLI/MCPB needs a separately justified non-caller boundary. Sources: workspace `docs/ARCHITECTURE.md`; ADR-0025; EPIC-004 context; [[TICK-203]], [[TICK-214]], and [[SIMPLI-012]].
- The existing renderer templates are not yet the accepted assessment-report contract described by `rendererref1`. The workspace catalogue includes general/fixed families such as `expert-report`, `repairable-contract-repair-report`, `total-loss-report`, `addendum-report`, `diminution-rebuttal`, `roadworthy-criminal-report`, valuation evidence and fee note; `rendererref1/report_data_schema.json` instead specifies a single assessment job containing four outcomes, computed cost rules, report/fee data and photos. A deliberate mapping/adaptation is required; template ids cannot be treated as capability ids. Sources: `TemplateCatalog.cs`; workspace `docs/ARCHITECTURE.md`; `reference/rendererref1/report_data_schema.json`; [[TICK-206]].
- `rendererref1` is supplied evidence, not a second policy owner. Its schema/design decisions need to be restated in FRD-11/Core types before implementation. It contains an internal contradiction: the design spec heading says “three assessment report outcomes” and later calls the three-value dropdown complete, while the table and JSON schema include the fourth `contract_repair` outcome. Sources: EPIC-004 context; docs authority chain; `reference/rendererref1/DESIGN_SPEC.md`; `report_data_schema.json`; [[TICK-204]].
- The supplied design explicitly leaves wording and identity data unaccepted: salvage paragraphs for categories N/A/B/N/A, recovery/storage wording, final statement of truth, and qualifications for E Mawdsley and N O'Reilly. Repository safety rules prohibit fabricating them or presenting a feature behind a closed gate as delivered. Sources: `reference/rendererref1/DESIGN_SPEC.md`; AGENTS.md safety rails; [[TICK-216]].
- RPT-03 cannot be implemented from the current evidence without resolving whether there is one canonical repair specification or conservative/maximised Audit specifications, and no accepted Audit renderer template exists. Sources: FRD-11/capabilities RPT-03; [[TICK-205]]; [[TICK-207]].
- The existing assessment persistence is not a render-ready aggregate. `Pegasus.Core/Assessment` and its Infrastructure persistence currently hold assessment values/findings and related review state, but `rendererref1` additionally needs principal/address, incident, vehicle, valuation, repair costs/worklists, history narrative, engineer/signature, fee and ordered photo inputs. DOCS-001 must assemble one immutable accepted input/version through Core rather than allowing the adapter to query or invent missing business data. Sources: `src/Pegasus.Core/Assessment/AssessmentContracts.cs`, `AssessmentOperations.cs`; `src/Pegasus.Infrastructure/Persistence/AssessmentEntities.cs`; rendererref1 schema.
- The render result already computes a PDF hash but has no Pegasus identity, durable job/idempotency record, template/payload version, custody reference, correction lineage or approval/send meaning. Those belong to the Core workflow and persistence introduced by DOCS-001, not the renderer adapter. Sources: workspace `RenderResult`; FRD-11; EPIC-004 context; DOCS-001.
- Current attachment handling accepts local paths by default and has a trusted-path escape hatch for cloud hosts. Integrated rendering must instead consume server-owned, custody-checked inputs; arbitrary local paths and MCP-local `file://` output are not acceptable production contracts. Sources: workspace `RenderRequest`; workspace architecture; FRD-11 custody/fail-closed rules.
- The design assets already have one canonical repository owner under `docs/design/assets/report-renderer/**` and `docs/design/brand/**`; the workspace project links them as embedded resources. Integration must preserve pinned logical resource names and verify the complete embedded set, without copying a competing template/brand truth into another layer. Sources: `CollisionRenderer.Core.csproj`; `docs/design/README.md`; SIMPLI-015 research.
- The current deployed topology is a Linux/AMD64 Container Apps Web host plus a .NET 10 isolated Flex Consumption Worker, Azure SQL, Storage queues/blobs, Box custody, managed identities and telemetry. The workspace's proven portable runtime is instead a Playwright Noble container that currently runs its standalone API and adds compatible fonts. Choosing the existing execution host requires proof for Chromium/native/font availability, lifecycle, concurrency, timeout and recovery; it must not silently create a new renderer service. Sources: `docs/operations.md`; workspace `Dockerfile` and `docs/ARCHITECTURE.md`; `infra/modules/platform.bicep`; [[TICK-215]] and PLAT-007.
- Workspace CI currently builds the independent solution on Windows and installs Chromium. Once integrated, its production sources/tests must join the main solution and application CI; the workspace lane, status register and architecture test that prohibit workspace references must be reconciled in the same change. Sources: `.github/workflows/workspaces.yml`; `workspaces/README.md`; `Pegasus.slnx`; `DependencyDirectionTests.cs`.
- Package reproducibility is not currently aligned: the application restores locked packages, while the renderer workspace has no committed package locks and uses its own build props. Integration must reconcile `TreatWarningsAsErrors`, .NET 10 settings, package versions and lock files with repository conventions. Sources: workspace `Directory.Build.props` and project files; application project lock files; [[TICK-211]] and [[TICK-212]].
- Existing renderer tests provide useful parity seams (fake PDF engine, validation/composition, browser launch, integration renders and MCP translation), but caller-backed acceptance requires new Core policy tests, Infrastructure adapter tests, composed Worker/Web tests and representative visual/PDF evidence against rendererref1 samples. A green workspace build alone is not integration evidence. Sources: workspace test projects; ADR-0009/0025; docs engineering evidence tiers.

## Implications

- Implement this as a coordinated sequence: SIMPLI-014 moves the proven engine into Infrastructure and establishes the Core port; DOCS-001 supplies the accepted assessment caller, immutable job/result identity and custody; PLAT-007 composes and proves it in the existing Azure topology. Their changes may overlap and must be planned serially where they touch project, DI, build and documentation files.
- Preserve one policy owner. Core defines render readiness, accepted input, template selection, calculations/variant rules, idempotency, version/reference/hash/provenance and correction lineage. Infrastructure only validates/serializes the Core request into the rendering engine and returns bytes plus technical metadata.
- Do not migrate the standalone API/MCP host into production. Retain only engine code and tests that serve the application caller; archive/remove workspace-only hosts and CI as their functions are replaced or explicitly deferred.
- Treat rendererref1 as acceptance evidence to translate into FRD/Core contracts, not as runtime JSON authority. Resolve its product contradictions and placeholders before claiming all assessment variants are deliverable.
- The likely runtime caller is durable queued Worker work because rendering is resource-heavy and retryable, but the present Flex Consumption runtime differs from the proven Playwright container. TICK-215/PLAT-007 must prove a supported in-topology execution shape or raise the narrow ADR required to alter the existing deployable boundary.
- The plan must enumerate template/capability mapping and disposition, all embedded assets/logical names, representative samples, package/runtime dependencies, and recovery/idempotency tests; “copy CollisionRenderer.Core” is insufficient and would violate the architecture boundary.
- Current-state and operations docs change only after the integrated caller/deployment is actually proved.

## Open questions

- Technical details still to prove during planning/execution: the exact Worker/Web execution host within the accepted topology, lifecycle of a shared Chromium engine, durable queue/job schema, artifact-custody adapter, and template migration mapping.
