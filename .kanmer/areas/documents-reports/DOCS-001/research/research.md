# Research — complete-assessment report trigger and immutable report custody

## Question

What exists on merged `origin/dev` for detecting a complete accepted assessment, rendering it exactly once per accepted input version, and retaining immutable report identity, hashes, provenance, custody, retries, and correction lineage? What must land before DOCS-001 can be planned safely?

## Verified baseline

Read-only inspection used merged `origin/dev` at `b548b674e31d05de6f43eeb285a25dedd7d2a768`, including SIMPLI-014 / PR #415. TICK-093 is active on an unmerged worktree; its branch was treated only as dependency status, not as source authority. No Azure or external write was performed.

## Findings

1. **The renderer boundary is merged, but only as an explicitly caller-supplied draft operation.** `AssessmentReportSnapshot`, `GenerateAssessmentReportDraft`, and `IAssessmentReportRenderer` now live in Core; Infrastructure supplies one Playwright adapter and Web composes it with `AddPegasusReportRendering`. The only callers are tests. The returned assessment and fee-note artifacts carry bytes, SHA-256, page count, template version, and engine version, but no Case/report identity or persistence. Source: `src/Pegasus.Core/Reports/AssessmentReportRendering.cs`, `src/Pegasus.Infrastructure/Reports/PlaywrightAssessmentReportRenderer.cs`, `src/Pegasus.Infrastructure/DependencyInjection.cs`, `src/Pegasus.Web/Program.cs`, caller search.

2. **Existing assessment readiness is necessary but not the renderer's complete accepted-input contract.** `AssessmentPolicy.EvaluateReadiness` checks many case/assessment fields and emits one blocker per unconfirmed field/estimate line. It currently checks presence rather than deriving an immutable snapshot and does not cover all renderer inputs: principal/report addressee and external reference, incident date, inspection mode presence, selected ordered current images and content bytes/custody, canonical raw cost components/display sections, source identities/versions/hashes, or exact accepted renderer engineer tuple. Its total-loss vocabulary also permits categories for which the active renderer intentionally has no approved wording. Source: `AssessmentPolicy.cs`, `AssessmentContracts.cs`, merged report snapshot validation, FRD-11.

3. **Assessment writes are durable and idempotent as edits, but they are not report-generation triggers.** `SaveAssessment` validates, persists under a serializable transaction with expected Case version, edit lease, operation-key/request-hash replay, permanent action/case history, increments the shared workflow version, and returns recalculated readiness. It does not enqueue or invoke rendering. A save can occur in Not ready, Review, or Report preparation. Therefore the real trigger seam is the committed accepted-data transaction/result—not the Razor page and not the renderer adapter—but it cannot be attached until TICK-092 defines the single immutable accepted snapshot. Source: `AssessmentOperations.cs`, `EfCaseAssessmentStore.cs`.

4. **Starting Case work is not the completeness trigger.** `StartCaseWork` moves an assigned Review case into Report preparation but does not evaluate assessment report readiness. Report preparation is the lifecycle area in which generation/approval belongs, yet equating this transition with “complete assessment” would render too early. Conversely, requiring a new staff button would contradict the operator-approved automatic complete-assessment trigger. Source: `CaseLifecycle.cs`, FRD-11, EPIC-004 context.

5. **TICK-092 is the hard structured prerequisite and is not implementation-ready.** Its approved plan owns the consistent derived snapshot/query and deterministic payload hash, explicitly leaving render-request/reference creation and result persistence to DOCS-001. TICK-092 is blocked by TICK-093 and TICK-094. TICK-093 is implementing and not merged; TICK-094 is still preparing and itself waits for merged TICK-093. The current merged `dev` therefore has neither an accepted canonical repair-specification version nor the accepted Engineer-decision component that TICK-092 must compose. Planning DOCS-001 now against current row models would duplicate or pre-empt those owners. Source: structured Kanmer dependencies and full TICK-092/093/094 research, plans, checklists, and questions.

6. **No durable report aggregate or report-generation job exists.** The database has report approval and exact Sent evidence, but approval stores only one artifact identity/hash on the current workflow record. There are no report request, report version, assessment/fee-note artifact, payload identity, source provenance, generation state, attempt, lease, or failure tables/ports. Reusing `CaseReportApproval` would collapse generation into human approval and lose the fee-note pair and correction history, contrary to FRD-11. Source: `CaseWorkflowContracts.cs`, `CaseWorkflowEntities.cs`, `CaseWorkflowModelConfiguration.cs`, `PegasusDbContext.cs`.

7. **Existing durable-work conventions are reusable, but the report job needs its own case-owned contract.** Intake, custody, vehicle lookup, and polling already demonstrate pending/claimed/lease-expiry/attempt/retry/terminal-failure, operation-key replay, request hashes, compare-and-swap, and visible Operations state. Rendering is a local in-process effect rather than custody work, so it should reuse those conventions rather than overload `ExternalWorkItem` or create a generic job abstraction without another concrete caller. Source: `DurableIntake.cs`, `ExternalWorkProcessing.cs`, `CustodyContracts.cs`, `LookupWorkItem.cs`, corresponding EF stores.

8. **Generated artifact custody can reuse document content storage mechanics, not the existing staff upload command unchanged.** `IDocumentContentStore` already stores immutable bytes by case/document-version identity, verifies SHA-256/length, and treats identical content as replay. Managed documents already support `DocumentSource.Generated` and `DocumentSemanticRole.EngineerReport`. However `AddCaseDocumentCommand` requires a user-style Case mutation, expected Case version, and edit lease; generation needs a system-owned atomic result boundary. Fee note also has no explicit semantic role. A report result must retain both typed artifacts, their version identities/hashes and content addresses without representing a generated draft as approved or sent. Source: `DocumentContracts.cs`, `EfDocumentCustodyStore.cs`, FRD-11.

9. **The idempotency key is derivable without an operator choice once TICK-092 lands.** The stable logical key is Case + active assessment family + deterministic accepted payload hash + template version (and calculation policy/version supplied by the accepted snapshot). An exact replay returns/reconciles the same request and artifact identities; a changed accepted payload or template produces a new immutable report version. Random execution operation keys alone are insufficient, because two callers could otherwise create duplicate reports for the same accepted input. This is an inference from FRD-11, the ticket contract, TICK-092's planned deterministic hash, and existing request-hash replay conventions.

10. **Correction lineage must be append-only and separate generated/approved/sent finality.** A newly accepted input hash after a prior generated result creates a successor report version and keeps the prior assessment/fee-note bytes, provenance, approvals, and Sent evidence. Existing `CaseWorkflowRecord.ReportApproval` and `ReportSentEvidence` are single current links, so they cannot alone preserve version-specific approval/sent association through correction. DOCS-001 can own generated-version identity and predecessor/successor lineage; TICK-208 remains the owner of preserving final Sent evidence through correction, and TICK-100 owns addendum behavior. Source: FRD-11, TICK-208, TICK-100, current workflow schema.

11. **Status/failure presentation has no current report-generation projection.** The assessment page exposes readiness and AI state only. There is no Pending/Rendering/Generated/Failed/Retry state, artifact download, or link from a generated version to approval. The UI must remain truthful: generation is a draft and never approval, issue, sending, or receipt. Source: `Pages/Cases/Assessment/Index.cshtml(.cs)`, FRD-11.

## Exact readiness and gaps

**Ready/reusable now:** merged Core renderer port/use case and closed four-outcome contract; Web-only renderer composition; assessment confirmation/readiness vocabulary; serializable Case mutation/idempotency/history conventions; immutable document content storage with hash verification; durable lease/retry patterns; report approval and exact Sent evidence boundaries.

**Not ready / absent:** merged TICK-093 canonical accepted repair-spec version; TICK-094 accepted Engineer-decision component; TICK-092 consistent accepted report snapshot/query/payload hash; automatic committed-data trigger; report request/version/reference aggregate; typed assessment+fee-note artifact persistence; report-specific content-custody transaction; retry/lease/failure projection; correction predecessor lineage; version-specific approval/Sent linkage; staff status/download surface.

## Implications for DOCS-001

- Keep DOCS-001 in Preparing and do not write a concrete implementation plan until TICK-093, TICK-094, and TICK-092 merge and their actual contracts are re-read.
- Consume TICK-092's snapshot/query verbatim; do not remap assessment policy or maintain a second required-field list.
- Attach enqueue/idempotency to the committed accepted-snapshot boundary. Rendering itself must occur after durable request creation, under lease/retry protection, because Chromium work cannot share the source-data database transaction.
- Persist the fixed assessment+fee-note pair as one report version with distinct typed artifacts and immutable hashes/content addresses.
- Preserve every version and its provenance. Exact replay returns the existing version; a new accepted payload/template identity appends a successor.
- Integrate later approval/Sent evidence by artifact/report-version identity without treating generation as either event.
