# Research — INTK-042: publish committed intake and custody work immediately

## Question

Where does the current durable intake/external-work hand-off wait, and what is the smallest coherent change that can publish committed work immediately without moving processing into Web, weakening the SQL durability boundary, or duplicating queue policy?

## Findings

- `ReceiveIntake.ExecuteAsync` stages source bytes first and then calls `IIntakeWorkStore.ReceiveAsync`; `EfIntakeWorkStore.ReceiveWithRetryAsync` writes the staged receipt and a `pending` work row, saves, commits, and only then returns the staged receipt id. No queue publication occurs in that receipt path. Sources: `src/Pegasus.Core/Intake/DurableIntake.cs`, `src/Pegasus.Infrastructure/Persistence/EfIntakeWorkStore.cs`.
- The current intake dispatcher is a second asynchronous hand-off. `DispatchPendingIntakeWork` claims the next due `pending|retry_scheduled` row under a one-minute dispatch lease, sends only the staged receipt id through `IIntakeWorkEnqueuer`, then marks the row `dispatched`; on send failure it returns the row to `pending` with a 30-second due time and rethrows. `ClaimProcessingAsync` refuses `pending` work, so sending an id directly without the claim/mark protocol would not start processing. Sources: `src/Pegasus.Core/Intake/DurableIntake.cs`, `src/Pegasus.Infrastructure/Persistence/EfIntakeWorkStore.cs`.
- `PendingWorkDispatchFunction` is the only live caller of the combined pending dispatcher and is timer-triggered. Production Bicep currently schedules it every five seconds, while staged-artifact reconciliation runs every ten seconds. The comment explicitly describes the timer as upload dispatch latency. Sources: `src/Pegasus.Worker/IntakeFunctions.cs`, `src/Pegasus.Core/Custody/ExternalWorkProcessing.cs`, `infra/modules/platform.bicep`.
- Manual upload ends after `IGroupedIntakeSubmission.ExecuteAsync` durably stages each member and redirects to status; Web never calls a dispatcher. Mailbox receipt also calls the same `ReceiveIntake` path from Worker, so both entry routes share the same avoidable post-commit timer wait. Sources: `src/Pegasus.Web/Pages/Upload.cshtml.cs`, `src/Pegasus.Core/Intake/GroupedIntake.cs`, `src/Pegasus.Core/Intake/MailboxIntake.cs`.
- External work already uses the same durable lease/enqueue/mark pattern: `DispatchPendingExternalWork` claims a committed row, queues its stable work id, and marks it queued; a send failure releases it to `pending` for replay. The combined `DispatchPendingWork` runs intake first and external work second. Sources: `src/Pegasus.Core/Custody/CustodyContracts.cs`, `src/Pegasus.Core/Custody/ExternalWorkProcessing.cs`, `src/Pegasus.Infrastructure/Persistence/EfExternalWorkStore.cs`.
- Custody work is committed in the same transaction as the business transition in several stores: formal Case acceptance creates `create_case_custody`; linked replacement creates the same kind; Image Intake registration creates `create_image_case_custody`; Image Intake merge creates `merge_image_case_custody`. Vehicle lookup rows share `ExternalWorkItems` but are a different kind, so “custody” cannot safely be inferred from the table alone if targeted publication is introduced. Sources: `src/Pegasus.Infrastructure/Persistence/EfCaseAcceptanceStore.cs`, `EfLinkedCaseReplacementStore.cs`, `EfImageIntakeStore.cs`, `EfVehicleWorkflowStore.cs`.
- Existing command results already expose the custody work id for formal Case acceptance and linked replacement. Image Intake operations do not consistently expose the newly created external-work id, so a design that requires every caller to carry an id would change more business contracts than the timer-led scanner does today. Sources: `src/Pegasus.Core/Cases/CaseContracts.cs`, `src/Pegasus.Infrastructure/Persistence/EfCaseAcceptanceStore.cs`, `EfLinkedCaseReplacementStore.cs`, `src/Pegasus.Core/ImageIntake/ImageIntakeContracts.cs`.
- The concrete Azure queue adapters and all queue-client/provisioning types currently live in `Pegasus.Worker`. Web cannot reuse them because Web and Worker are sibling composition roots. `Pegasus.Infrastructure` is the established shared adapter layer and already depends on Azure Identity/Blob packages, but it does not yet reference `Azure.Storage.Queues`. Sources: `src/Pegasus.Worker/AzureQueueIntakeWorkQueue.cs`, `AzureQueueExternalWorkQueue.cs`, `WorkerAzureClientFactory.cs`, project files, ADR-0002 dependency rules.
- Production grants the Worker Storage Queue Data Contributor at the transport account, but Web has no queue sender grant and receives no intake/external queue service URI settings. Immediate manual-upload publication therefore requires a narrowly scoped Web sender role plus queue endpoint configuration; code composition alone cannot make the deployed caller work. Source: `infra/modules/platform.bicep`.
- A synchronous post-commit caller must distinguish “publication failed” from “receipt failed.” The current dispatcher deliberately rethrows after releasing a failed claim. Reusing that exception unchanged from `UploadModel` would show a failure after bytes and the work row are already committed; recovery would still occur, but the operator-facing acknowledgement would be false and could invite a replay. Sources: dispatcher error paths and `UploadModel` recoverable-error handling.
- Queue delivery is already at least once. Completed/failed intake deliveries no-op, active processing leases prevent a concurrent duplicate claim, and external processing likewise claims durable work. Immediate publication and a slower recovery sweep can therefore coexist without a second processing owner. Sources: `ProcessQueuedIntake.ExecuteAsync`, `EfIntakeWorkStore.ClaimProcessingAsync`, `EfExternalWorkStore`, ADR-0002 data-consistency decision.
- FRD-02 currently says the Worker “dispatches pending work,” and ADR-0002 says a Worker-hosted SQL outbox dispatcher publishes ids. The approved parent ticket [[INTK-041]] must update those contracts before this ticket implements Web publication; this ticket must consume that target state, not silently contradict the current accepted text.
- [[INTK-003]] is a real prerequisite, not optional hardening. Once the fast path marks a claim dispatched, a lost queue message must be returned to a dispatchable state by slow recovery; current intake recovery only covers expired `dispatching|processing` leases, leaving unleased `dispatched` work stranded.
- [[INTK-040]] is currently claimed and has uncommitted changes in `DurableIntake.cs`, `GroupedIntake.cs`, `WorkerDependencyInjection.cs`, FRD-02, and overlapping intake tests. INTK-042 must not start implementation on those files until INTK-040 lands and the INTK-042 branch is based on the resulting `origin/dev`; this is current work ownership, not a compatibility requirement.
- The EPIC-002 group context requires consolidation without changing the ticket’s durable intake-processing owner. Immediate publication should therefore reuse one Core dispatch protocol and shared Infrastructure queue adapters, not create Web-specific queue policy.

## Implications

The safe target is still a transactional outbox: SQL commit remains first, then the receiving/application boundary asks the existing dispatch owner to publish immediately. The fast path must reuse the same claim, enqueue, mark, release, and idempotency rules as the recovery sweep; it must not send a raw id from `pending` or create a second Web implementation.

Planning must decide the narrow invocation points after inspecting the post-INTK-040 code. For intake, both manual upload and Worker mailbox receipt need the same post-commit publisher. For custody, publication must follow the use case/store commit that created the work, including Worker-created automatic Case/Image work and Web-created Case/replacement work. A targeted claim is attractive where a stable work id is already returned, but broad contract changes solely to transport ids should be avoided; one shared due-work dispatcher invoked immediately at the relevant boundaries may be simpler if tests prove it cannot starve or mislabel the just-committed work.

Immediate queue failure must leave the committed row recoverable and emit telemetry, but must not report that durable receipt/case creation itself failed. The recovery timer becomes a one-minute safety net after [[INTK-003]] rather than the ordinary transport. The existing five-second polling schedule and comments then become obsolete and must be replaced with the parent contract’s slower recovery cadence.

Implementation must wait for both [[INTK-041]] and [[INTK-003]], and for the actively owned overlapping INTK-040 change to merge. It should then move the queue adapters/common transport composition to Infrastructure, compose them in Web and Worker, add only the Web queue-send permission/configuration required by the real caller, and retain Worker as the sole queue processor.

## Open questions

None requiring an operator decision. The approved route fixes ownership, recovery cadence, and queue-failure semantics; the exact shared publisher signature is an implementation choice to settle in planning against the post-INTK-040 code.
