# INTK-014 research — image-case Box custody

## Verified facts (read-only checks, 2026-08-20, worktree at origin/dev 0449e6ec)

- **Box custody is case-scoped only.** The single Box writer path is the external-work queue: `EfCaseAcceptanceStore.AcceptAsync` (and `EfLinkedCaseReplacementStore`) insert an `ExternalWorkItems` row `Kind=create_case_custody` keyed on `CaseId`; `EfQueuedCustodyProcessor.ExecuteAsync` processes it via `ICaseCustody` (`src/Pegasus.Core/Custody/CustodyContracts.cs`). Production DB confirms: only 2 `ExternalWorkItems` rows ever, both `create_case_custody`, keyed on CaseId (prod diagnostics 2026-08-20).
- **ImageIntakes has no custody column** (`src/Pegasus.Infrastructure/Persistence/ImageIntakeEntities.cs`) and no code path creates a Box folder for an image-initiated case. Missing feature, not a failure.
- **`ExternalWorkItemEntity.CaseId` is a non-nullable FK to Cases** (`PegasusDbContext.cs:1153`), so image-keyed work needs a schema change: `CaseId` becomes nullable and a nullable `ImageIntakeId` FK is added.
- **INTK-015 (merged) made the submission group the registration unit**: `ImageIntakes.SubmissionGroupId` (filtered unique index), `EfImageIntakeStore.RegisterAsync` registers the whole group in one transaction and moves every image-only member receipt to `ImageIntakeRegistered`.
- **Merge choreography owner**: `ImageIntakeCasePairing.SyncMergeAfterLinkAsync` → `IImageIntakeStore.MergeAsync` → `EfImageIntakeStore.TransitionAsync` (serializable transaction, operation-key replay, lifecycle event row). All three merge entry points (forward automation, reverse pairing, manual link) funnel through it.
- **Root fencing already exists**: every Box object access goes through `BoxContentClient.EnsureDescendantAsync`, which walks ancestry to `Box:RootFolderId` (405543781910) and refuses anything outside it or in trash. New move/delete operations get the same fence by construction if they go through `BoxContentClient`.
- **Retry conventions in this queue**: (a) terminal `failed` + staff retry (`IExternalWorkRetryStore.RetryAsync` from the Operations page; `RetryCaseCustody` for case custody); (b) re-arm as `pending` with a future `DueAtUtc` — an existing convention used by vehicle lookup (`LookupWorkItem.cs`: `RetryScheduled` → `pending` + backoff delays, attempt cap). Queue-level Functions redelivery does NOT retry custody work because a failed row returns early from the processor.
- **Fail-safety**: images are authoritative in blob custody (`IntakeAssets` + `IIntakeArtifactStore`, pegcustody container). Box work is asynchronous (outbox dispatch via `PendingWorkDispatchFunction`), so a Box outage can never block registration or merge — both only insert a queue row in their own transaction.
- **Operations visibility**: the Operations page projection (`EfOperationsStore` workRows) inner-joins `ExternalWorkItems`→`CaseWorkflows` on CaseId. Merge work can carry the target CaseId and therefore appears there with generic retry; create work (no case yet) will not appear — its state is recorded on the ImageIntake row instead, and it self-retries with backoff on dependency failure.
- **Local testing**: `LocalCaseCustody` is the composed adapter outside production (`DependencyInjection.cs:341`); `tests/Pegasus.IntegrationTests/ProductionBoxCustodyTests.cs` has a `StatefulBox` in-memory Box fake (currently rejects DELETE and has no move) — extend it for move/delete. NO live Box calls from this task; production verification is deploy-stage.

## Assumptions (not verified by check)

- The operator's "its contents moved out of its Box folder into that case" is satisfied by moving the image files into `Evidence/Images` under the instruction case's Box root (consistent with the existing `Evidence/Original instruction` layout), then removing the emptied image-case folder.
- Group adoption after custody processing (a rare race where a single-receipt registration is adopted into a group after its create-custody work already completed) may leave later-adopted members' images out of the Box folder; blob custody remains authoritative and the merge move carries whatever the folder holds. Accepted as a bound of this slice.

## Design decisions

1. **Reuse `CreateCaseRootAsync` for the image-case folder.** The image-case folder is exactly a bound root folder named for a reference (`AU17SEO-01`) under the approved root — the staged-create + binding-file machinery in `BoxCaseCustody.GetOrCreateBoundFolderAsync` is reused as-is with the ImageIntake id in the id slot and the Image Intake Reference as the reference. No duplicate folder-creation implementation.
2. **Two new port operations on `ICaseCustody`** (default implementations throw, so existing fakes keep compiling and fail closed): `RetainImageCaseAssetAsync` (upload one group image as `NNN <safe filename>` into the image-case root, hash-verified, idempotent by name+content) and `MergeImageCaseContentsAsync` (move every image file into `Evidence/Images` under the case root, delete the binding file, remove the emptied folder — non-recursive delete so unexpected content fails closed).
3. **Two new work kinds** in `ExternalWorkKinds`: `create_image_case_custody` (enqueued in `EfImageIntakeStore.RegisterAsync`'s transaction) and `merge_image_case_custody` (enqueued in `EfImageIntakeStore.TransitionAsync`'s merge branch, carrying the merged-into CaseId so it appears on the Operations page). Both routed to the existing `EfQueuedCustodyProcessor`.
4. **Custody state on the ImageIntake row** (new nullable columns, no new table → no grant census change): `CustodyState` (null legacy / pending / confirmed / merged / failed), `CustodyRootRemoteId`, `CustodyConfirmedAtUtc`, `CustodyMergedAtUtc`.
5. **Retry**: dependency failures (`custody_dependency_failure`) re-arm `pending` with vehicle-lookup-style backoff up to an attempt cap; other failures and the cap are terminal `failed` with `CustodyState='failed'`. Merge work additionally retries when the create work has not completed yet (ordering race).
