## Scope additions from the coordinator (handled before this document was finalised)

Two production defects were assigned mid-task, both in `wwwroot/js/site.js` which this ticket owns:

1. **Drag-and-drop reported broken in production.** Investigated with two faithful reproductions against the real rendered `/Upload` page (a page-level synthetic `DragEvent` carrying a real `DataTransfer`, and a CDP-level native drop via `Input.dispatchDragEvent` with real file paths and real hit-tested coordinates) — both **passed** against current `dev` HEAD. **Verified**: the reported failure does not reproduce for a drop landing inside `[data-dropzone]`. The coordinator then supplied the real root cause: `site.js` binds `dragenter/dragover/drop` only to the small dashed rectangle, so any drop landing elsewhere in the window (a heading, a panel border) is unhandled and Chrome's default action navigates the tab away. **Verified** by code read (`site.js:119-177` pre-fix had no document-level handler) and by a regression test that failed pre-fix and passes post-fix (below).
2. **INTK-011 (sibling ticket, not mine): grouped image members can terminal-decide independently** (one registers as an ImageIntake, its sibling goes `needs_sorting`, in the same group). Not fixed here — Core routing race, out of scope — but the confirmation-step design below reads each member's outcome independently from the read model rather than assuming one outcome per group, so a split group is reported honestly rather than papered over.

Fixed in `src/Pegasus.Web/wwwroot/js/site.js`: document-level `dragover`/`drop` safety net (`preventDefault()` when nothing more specific already did) plus widening the effective drop target from the dashed rectangle to its containing `.panel` (dragenter/dragleave depth-counted; existing `.dropzone.is-dragover` CSS reused as-is). New tests: `tests/Pegasus.IntegrationTests/Browser/UploadDropzoneBrowserTests.cs` (4 tests — in-zone page-level drop, in-zone CDP drop, panel-but-outside-zone CDP drop [red before the fix, green after], off-panel CDP drop does not navigate/misroute).

## What exists today (main ticket scope)

### The Upload page and its single group POST

- `src/Pegasus.Web/Pages/Upload.cshtml.cs:51-181` — `OnPostAsync` reads every selected file into memory, then calls `groupedSubmission.ExecuteAsync(...)` **once**, synchronously, for the whole batch (`Upload.cshtml.cs:130-136`). On success it redirects to `/UploadStatus/{id}` for a one-member group (`:141-151`) or `/UploadGroupStatus/{id}` otherwise (`:153-155`). **Verified**: there is exactly one POST per submission; no per-file endpoint exists, and the docstring at `:12-27` states storage is durable before the redirect — Worker owns every later transition.
- `src/Pegasus.Core/Intake/GroupedIntake.cs:109-187` (`SubmitGroupedIntake.ExecuteAsync`) — stores members **sequentially inside the one request** (`:148-173`, a `foreach` with `await submission.ExecuteAsync` per file). Each member becomes durable (a staged receipt) before the loop moves to the next; the whole group's storage completes before the HTTP response is sent. **Verified** by reading the implementation directly.
- **Consequence (verified, not assumed): there is no way for the browser to observe per-file storage progress *during* the POST.** A single `fetch` gets one response after the whole batch is already stored (or the whole batch failed — `Upload.cshtml.cs:96-99,157-178` reject the entire submission on any validation error or the first unrecoverable exception; nothing is partially stored on that path). The only truthful per-file signal available to the client is the **result of the completed POST** (`GroupedIntakeSubmissionResult.Members`, each carrying `StagedReceiptId`/`IsDuplicate`, `GroupedIntake.cs:30-32`) and, after redirect, **the existing status read model** polled by `data-auto-refresh` (`IQueuedIntakeStatusQueries.GetAsync`, `DurableIntake.cs:116-121`), which reports each member's `Received/Processing/Complete/Failed` state independently.
- The ticket's own honesty rule ("if per-file granularity is genuinely unavailable during the POST, rows enter a processing state together and tick individually as the status read model reports each file stored") is therefore the only design the backend supports without a second endpoint. **Chosen design**: fetch-submit the existing form; every row shows a spinner together for the duration of the POST (this is the truthful bound — no finer signal exists); on a successful response, each row ticks using the real per-member data the response actually returned (not a blanket "done" flash); a validation failure re-renders the page exactly as today (native fallback) and every row shows the file-level error text already produced by `Upload.cshtml.cs:78-94`, matched back to its row by array index.

### The recognition/routing outcome data the confirmation step can honestly read

All of the following are **verified by reading the actual contracts**, not assumed:

- `Pegasus.Core.Intake.QueuedIntakeStatus` (`DurableIntake.cs:87-94`): `Status` (`Received/Processing/Complete/Failed`), `CaseId`, `ProcessedReceiptId`, `FailureCode`. This is what `UploadStatus`/`UploadGroupStatus` already query.
- `Pegasus.Core.Intake.IntakeReceipt` (`IntakeContracts.cs:356-396`) carries `Decision` (`IntakeContracts.cs:77-86`: `CaseCreated, NeedsSorting, BlockedIntake, Unsupported, OcrRequired, TechnicalFailure, ImageIntakeRegistered`), `CaseMatchDecision` (`CaseMatchEvaluationResult`), and `CurrentCaseId` (`AcceptedCaseId`/`ManualLinkedCaseId`). Reachable via the existing `IGetIntake.ExecuteAsync` (`IntakeQueryUseCases.cs:43-63`), the exact port `/Cases/Create` and `/Intake/Details` already use.
- **Automatic case association is channel-agnostic, verified**: `DurableIntake.cs:721-760` (`AssociateCaseIfUnambiguousAsync`) runs for *any* receipt whose `CaseMatchDecision.Outcome == CaseMatchOutcome.UniqueMatch` (images and instruction documents alike — nothing gates it to a source channel) and writes through `IAutomaticCaseAssociationStore.AssociateFromMatchAsync` before the receipt is ever shown anywhere. **Consequence**: by the time the confirmation step can render anything, a *definitive* single match is already attached — there is no reachable "unique match, not yet attached" state to offer as a staff decision. This resolves the ticket's INT-28 constraint precisely: automation's own bar is `UniqueMatch`; anything short of that (`Ambiguous`, `NoMatch`, `NoKeys`) is what the confirmation step's staff offer covers.
- `CaseMatchEvaluationResult.Outcome == CaseMatchOutcome.Ambiguous` with populated `Candidates` (`CaseMatchContracts.cs:98-112`) is therefore the genuine "a case was located, staff decides" state — multiple candidates exist, none was definitive enough to auto-attach.
- `Decision == ImageIntakeRegistered` means the automatic image-routing engine (INTK-006/008) already created an Image-initiated Case (VRM usable, no unique existing-case match) — this is **also always automatic**, never a staff-triggered creation (an Image-initiated Case's reference *is* the VRM; it cannot be manually created without one — confirmed by INTK-008's own scope text: "Conflicting valid VRMs do not create an Image-initiated Case... INTK-007 owns one grouped Unidentified U<n> reference"). Resolvable to its id via `IImageIntakeQueries.GetByOriginReceiptAsync(receiptId, ...)` (`ImageIntakeContracts.cs:172-174`), and its page is `/VehicleImages/{id:guid}` (`ImageIntake/Details.cshtml:2`).
- Routing to Unidentified (INTK-007) is visible independent of `Decision` via `IUnidentifiedStore.GetByOriginAsync(origin, ...)` (`UnidentifiedContracts.cs:218-220`), checked at **both** `UnidentifiedOrigin.Receipt(receiptId)` and, for a grouped image submission whose whole group was kept intact (no usable/conflicting VRM), `UnidentifiedOrigin.SubmissionGroup(groupId)` (`UnidentifiedContracts.cs:44-47`; group registration confirmed reachable from `ImageIntakeAutomation.cs:121` via `groupStore.FindForMemberSourceAsync`). Its page is `/Unidentified/{id:guid}` (`Unidentified/Details.cshtml:1`). **Assumed, not exhaustively verified**: I read the contracts and one call site proving the group-level origin exists and is reachable, but did not read the full grouped-image Worker pipeline line by line (out of scope for this ticket, owned by INTK-006/007/011); the plan checks both origins defensively rather than asserting the exact trigger conditions.
- `IntakeDecisionPolicy.CanBecomeCase(Decision)` (`IntakeDecisionPolicy.cs:16-31`) is the existing, single-source check for "this can still become a case manually" — already used by `Intake/Details.cshtml.cs:67-70` (`CanCreateCase`). Reused as-is, not re-implemented.

### Existing manual-decision surfaces to route to (not reimplement)

**Verified by reading the actual page models**, this ticket's confirmation step is a decision *summary + routing*, not a second link/create engine — everything it offers already has a durable, tested implementation elsewhere:

- **Attach with override**: `src/Pegasus.Web/Pages/Intake/Details.cshtml.cs` already implements the full staff flow — `AssociationCandidates` (from `IImageIntakeCaseCandidates`/`CaseMatchDecision`), `OnPostClaimCaseLeaseAsync` (`:245`), `OnPostLinkCaseAsync` (`:282`, backed by `ILinkIntake`/`LinkIntakeRequest`, `IntakeContracts.cs:773-781,867-872`, which requires an edit lease on the target case — a genuine multi-step concurrency-guarded flow), and `OnPostReverseCaseLinkAsync` (`:318`, backed by `IReverseIntakeLink`, `IntakeContracts.cs:783-791,874-879`) for the reversal path the ticket names. Re-implementing this inline on the confirmation surface would duplicate a leased, replay-protected mutation — a stop condition. The confirmation step links to `/Intake/Details/{id}` instead.
- **Create a new (Instruction-initiated) case**: `src/Pegasus.Web/Pages/Cases/Create.cshtml.cs` — the one place `IAllocateIntake.AttemptStaffCreateAsync` is called from staff UI (`:16-27` remarks). Seeded from `receiptId` via `IGetIntake`. The confirmation step links to `/Cases/Create?receiptId={id}`.
- **Already-associated case**: `/Cases/Details/{caseId}` (existing).
- **Image-initiated case**: `/VehicleImages/{id}` (existing, INTK-008).
- **Unidentified**: `/Unidentified/{id}` (existing, INTK-007; INTK-009 is mid-flight restructuring its *list* surface, not this detail route, and does not touch `Pages/Upload*.cshtml`/`site.js`).

### CASE-003 — `/Cases/Create` 500

**Verified**: `src/Pegasus.Core/Intake/IntakeQueryUseCases.cs:43-63` (`GetIntake.ExecuteAsync`) throws `ArgumentException("An intake receipt identifier is required.", nameof(query))` whenever `query.ReceiptId == Guid.Empty`. `Cases/Create.cshtml.cs:213-221` (`OnGetAsync`) calls `LoadAsync(receiptId, ...)` → `getIntake.ExecuteAsync(...)` with no empty-Guid guard, so `GET /Cases/Create` with no `receiptId` (a stale bookmark, a mistyped confirmation link) throws uncaught, matching CASE-003's report exactly. **In scope here** because the confirmation step's own "Create a case" links always carry a real `receiptId`, but a defensive guard is cheap, correct, and exactly what CASE-003 already specifies (`NotFound()` before `LoadAsync` runs) — fixed as a small, targeted addition, not a redesign.

## Design decision this research settles (per the ticket's own instruction to state it, not ask it)

INT-28 interaction, restated precisely against the verified evidence above: automation's bar is `CaseMatchOutcome.UniqueMatch` (images and instructions alike) or a usable VRM with no unique match (images → Image-initiated Case). Both are **always** automatic and are **reported**, never re-offered, on the confirmation surface (with the existing reversal path linked for the case-attach report). Anything short of that bar — `Ambiguous` candidates, or a plain instruction document with `CanBecomeCase == true` and no match at all — is the **staff decision** the confirmation step actually offers, and it offers it by routing to the existing surface that already implements the mutation.
