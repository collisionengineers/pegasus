## Backfill research (VERIFY2, 2026-08-20)

Written retrospectively — the capability was already coded before this ticket was worked. This records the code-vs-capability-text comparison and, crucially, the production gate state.

**Capability text (`docs/capabilities.md:269`, AI-09, Now/0.1.0-alpha.1):** "Staff `Send to AI` creates one durable idempotent capability-scoped work request bound to an immutable case/version stamp; the hand-off carries a pointer only, and the scoped worker returns its work as attributed unconfirmed Automation Actor writes reviewed at manual engineer assignment, with delivery status and visible failure on the tracking record." The row's own note already states: *"Implemented behind `Features:SendToAi` (DevelopmentOffline evidence runs only; ADR-0021 rewords the contract from proposal-only worker to direct-writing worker)... the channels transport is a research preview that carries local evidence runs only, and production activation needs a separate non-preview transport decision."*

**Code match, clause by clause:**
- Durable idempotent capability-scoped work request: `src/Pegasus.Core/AiWork/AiWorkContracts.cs:33` `AiWorkRequestRecord`, `:106` `AiWorkRequestTransition` (`ExpectedVersion`, `:146` `operationKey`); persisted by `src/Pegasus.Infrastructure/Persistence/EfAiWorkRequestStore.cs`. Operation-key validation and duplicate rejection: `src/Pegasus.Core/AiWork/AiWorkOperations.cs:57,117-123` (`ValidateOperationKey`), `:135` `SendCaseToAi`.
- Immutable case/version stamp: `ExpectedVersion` on the transition, checked before any mutation (`AiWorkOperations.cs:57`).
- Pointer-only hand-off: `src/Pegasus.Web/AiWork/ChannelAiHandOffTransport.cs:1-16,25-30` — the outbound payload is exactly `{schema_version, request_id, case_reference, instruction}`; the class doc comment states explicitly "It sends the pointer (never case content)".
- Attributed unconfirmed Automation Actor writes reviewed at manual engineer assignment: ADR-0021 ("Automation Actor direct-write assessment contract and the Send to AI transport slice").
- Delivery status + visible failure on the tracking record: `ChannelAiHandOffTransport.cs` distinguishes terminal refusals (401/403/413/415) from transient failures (connection errors/5xx), matching "delivery status and visible failure."
- Round-trip integration coverage: `tests/Pegasus.IntegrationTests/SendToAiIntegrationTests.cs` (sets `Features:SendToAi=true` at `:190` to exercise it — confirming the test harness itself must force the flag on, because production leaves it off).

**Production gate state (the decisive fact for this ticket):** `SendToAi.FeatureFlag = "Features:SendToAi"` (`src/Pegasus.Web/AiWork/SendToAi.cs:12`). `SendToAiOptions.TryCreate` (`SendToAi.cs:28-43`) returns `null` (surface absent) unless the flag is set, AND if the flag is set while the runtime profile is not `DevelopmentOffline`, it **throws** `InvalidOperationException` at startup — enabling it in production is not merely undocumented, it is coded to fail closed. `infra/modules/platform.bicep` (production infra, confirmed by `git grep -n "SendToAi" infra/modules/platform.bicep` → zero matches) never sets `Features:SendToAi` anywhere; `ASPNETCORE_ENVIRONMENT=Production` is set at `platform.bicep:410`. Production therefore runs with the flag absent (defaults false) and the whole Send-to-AI surface composed out.

**Related work:** [[TICK-104]] (MCP-07, connector administration UI) is in `review` and is itself gated by this ticket per its own labels; [[SIMPLI-012]] (decision-record, done) relaxed the QDOS-alpha *scope-of-work* restriction on MCP tickets ("All MCP related tickets are within your scope now") but that is a permission-to-work decision, not a production-activation decision — it does not touch `Features:SendToAi` or the DevelopmentOffline-only restriction, which remains an explicit, coded, unresolved boundary.

**Verdict:** the capability is fully implemented and tested to the letter of its capability-text description, and the code is present on `origin/dev`/`origin/main` — but it is a closed composition gate in production: no app setting turns it on, and the code fail-closes if anyone tried to turn it on without also changing the runtime profile. A closed gate is not delivered. This ticket stops at `review` (implementation done, verified in code and tests) and does **not** proceed to `verifying`/`done`, since there is no live production behavior to verify and `deployment` cannot honestly be set to `production`.

**What production activation needs (recorded per lane instructions, not actioned):** (1) an explicit business/architecture decision to replace the research-preview loopback channel transport with a non-preview transport (the capability row already names this as the blocking decision); (2) once that decision is made, a follow-up ticket to set `Features:SendToAi=true` in `infra/modules/platform.bicep` for the production Web app and to relax or contextualize the `DevelopmentOffline`-only fail-closed check for whatever the accepted production transport turns out to be; (3) re-running this ticket's verification against the newly live surface before it can honestly reach `done`.
