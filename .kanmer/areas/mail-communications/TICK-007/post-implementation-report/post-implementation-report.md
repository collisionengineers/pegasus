## Post-implementation report (2026-08-20)

**What was built.** `EmailEvaluationWorkflow` (`scripts/email-eval-desktop/`) now populates its pre-existing, previously-always-null `Suggestion` display slot with the rule-generated category, subtype, matched-predicate evidence lines, and policy key/version, by calling the Core-owned `IMailClassificationPolicy` (`QdosMailClassificationPolicy`) — the same policy MAIL-21/22 shipped for in-app mail classification. No second classification implementation was created; the desktop tool references `Pegasus.Core` (already a `ProjectReference` in its `.csproj`, per ADR-0016) and calls the one existing policy owner. A second dead dependency (`IIntakeSourceReader sourceReader`, injected but never called) was put to its evident intended use rather than adding a new one.

**Caller / contract.** `EmailEvaluationWorkflow.LoadCurrentAsync` (private, called from `SelectFolderAsync`/`SkipAsync`) builds an `IntakeSource` from the already-read message bytes (`ManualUpload` channel, SHA-256-of-content as the receipt token — same convention as `DownloadIntakeSource.cs`), reads it via the existing `IIntakeSourceReader`, classifies via `IMailClassificationPolicy.Classify`, and renders the result into `suggestion`. `MainForm` renders it unchanged (just a wider, wrapping label now).

**Failure behavior.** Classification is wrapped in its own `IntakeExceptionPolicy.IsRecoverable` guard, separate from the display-read guard. A rule-evaluation fault degrades to no suggestion ("No category") — it never blocks displaying or filing the message. Unclassified outcomes (no predicate matched) also render as "No category" — nothing to suggest is not a failure. The human reviewer's own category selection remains the one persisted as the filed category; the rule suggestion is recorded alongside it in the JSONL log's pre-existing `suggestedCategory` field, read-only.

**Tests.** `scripts/email-eval-desktop/tests/DesktopEvaluatorTests.cs` — `dotnet test`: **9 passed, 0 failed** (8 pre-existing + `RuleClassifiedEmailPopulatesCategorySubtypeEvidenceAndPolicyVersion`, a deterministic fixture: an in-memory `.eml` with an `Automatic reply:` subject, asserting the exact rendered suggestion string including category, subtype, the one matched predicate's evidence text, and `policy qdos_mail_classification v3`). `dotnet build` of both the exe and test projects: 0 warnings, 0 errors.

**Scope extension delivered in the same branch/PR (orchestrator instruction).** TICK-004 (EVAL-02) was reverted to preparing with hard evidence that `CategoryCatalog.Load` depended on a taxonomy file (`docs/reference/CollisionSPikeCurrenttree.txt`) deleted in commit `4e084ca2`, making the evaluator unstartable. Fixed per ADR-0016's own stated ownership: `CategoryCatalog.Load()` now sources the 8 Received + 4 Sent categories from Core's `MailTaxonomy` directly (no file, no local copy of the taxonomy). While fixing this, a second, independent break was found and fixed: the tests' fixture `.eml` file path also no longer existed (an unrelated rename), so all file-based test fixtures were replaced with in-memory MimeKit-built messages, matching the existing `IntakeTestEvidence.CreateEmail` convention used elsewhere in the repo. TICK-004's own `files.md`/`plan.md`/`post-implementation-report.md` were updated in place to record this fix over their earlier (correct-at-the-time) "no files changed, verification-only" statements.

**Local-only boundary.** No Outlook/Box/Azure/database/deployment touch. The desktop project remains outside `Pegasus.slnx` (ADR-0016). All test fixtures are synthetic, built in-memory — none of `corpus/`'s real, immutable local email data was read, copied, or referenced.

**Left out / parked.** Checklist item "Run provider-specific instruction-email categorisation against real `.eml` files through the local folder-based evaluator" is left unchecked — it is a manual, interactive GUI smoke check against a reviewer's own real files, not something this automated pass can perform (and `corpus/` may not be used for it per repository rules). No operator question was raised; nothing else was deliberately left out of either ticket's scope as given.
