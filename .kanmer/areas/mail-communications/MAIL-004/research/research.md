# Research — MAIL-004

## Question

What is the smallest administrator-owned approved Outlook-category catalogue that gives MAIL-13 a real fail-closed caller contract, without inventing speculative search/linking behavior or a generic mailbox-rule editor?

## Verified findings

- **Current ref inspected directly:** `origin/dev` at `a3c88a7b`. MAIL-004, MAIL-002, TICK-051/052/053/054, both epic contexts, FRD-08/12, design/access rules, current administration/Core/EF/Graph/Web code and focused tests were read.
- **There is one concrete downstream business caller.** TICK-054's resolved MAIL-13 contract requires exact-message add/remove of one configured approved Outlook category and explicitly rejects arbitrary category strings. MAIL-004 is now a stored `blocks` predecessor of TICK-054. If MAIL-13's category action is later removed or archived, this catalogue has no independent product outcome and MAIL-004 should be archived without code.
- **No catalogue or Outlook-category projection exists today.** `origin/dev` contains no approved-category entity, Core port/use case, EF store, administration page, Graph master-category adapter, or retained-message category field. The word “category” in current Core primarily means Pegasus mail classification (`MailCategory`), which is a different concept and must not be reused as Outlook label policy.
- **MAIL-002 supplies the administration convention to reuse.** The merged `/Administration/Mailboxes` flow derives an authenticated Administrator actor, enforces `ManageApprovedMailboxes` in Core, uses versioned/idempotent reasoned updates, permanent `ActionHistory`, hidden internal plumbing, honest failure, accessible forms, and server-side Graph identity resolution. MAIL-004 should reuse those policy/update/test shapes, not append Outlook-category fields to `ApprovedMailboxEntity` or expose tenant identifiers.
- **The smallest policy owner is one global Pegasus allowlist of display names.** It needs one internal id, exact trimmed display name, Active/Disabled state and version. Updates require Administrator authorization, expected version, operation key and reason; duplicates are rejected and rows are disabled rather than deleted. MAIL-13 receives/posts only the internal catalogue id, reloads the active row server-side, and supplies its display name to the Graph action. This is one list per concept and works consistently across all approved mailboxes.
- **Do not duplicate Outlook's master-list facts.** Microsoft Graph defines each mailbox/user's master categories by a unique `displayName` plus color; item assignment uses the display name. Color and Graph category id belong to Outlook, not Pegasus policy, and are not required by MAIL-13. Storing them would create a second drifting catalogue. Official source: https://learn.microsoft.com/en-us/graph/api/resources/outlookcategory?view=graph-rest-1.0
- **Approval and Outlook existence are separate facts.** MAIL-004 should configure only the Pegasus allowlist and perform no Graph read/write. At MAIL-13 action time, the exact mailbox adapter may validate that the configured name exists in that mailbox's master list before assignment, then fail closed if absent. Listing master categories requires the separate application permission `MailboxSettings.Read`; it is not implied by current `Mail.Read` or planned `Mail.ReadWrite`, and requires the normal exact permission/RBAC approval. Source: https://learn.microsoft.com/en-us/graph/api/outlookuser-list-mastercategories?view=graph-rest-1.0
- **Automatic master-list synchronization is out of scope.** Creating/updating/deleting Outlook master categories requires `MailboxSettings.ReadWrite`, is an external mailbox-settings write, and introduces cross-mailbox drift/reconciliation and destructive semantics not requested by MAIL-13. MAIL-004 must not grant permissions, synchronize colors, create missing categories, or delete Outlook categories. Source: https://learn.microsoft.com/en-us/graph/api/outlookuser-post-mastercategories?view=graph-rest-1.0
- **MAIL-13 must preserve unrelated item categories.** Graph message PATCH writes the `categories` collection. The exact-message action must read current provider state, add/remove only the resolved configured display name, preserve every unrelated label, version-check/replay through MAIL-13's operation convention, and record before/after history. MAIL-004 owns only approval, not message mutation.
- **MAIL-11 search is not a caller.** TICK-053 and FRD-08 settle search over retained body, attachment filename and searchable attachment content within mailbox/folder scope. `IRetainedMailQueries` has no category filter; retained entities store no Outlook categories; adding one would require new polling/projection/index/UI/MCP scope with no accepted behavior. Do not add category search fields, indexes or filters.
- **Automatic and manual Case association are not callers.** TICK-051 accepts only system-wide unique normalized VRM or mailbox-scoped exact thread evidence. TICK-052 uses deliberate canonical Case search and reasoned link/unlink/relink. Both explicitly keep classification, folder/category state and Case association separate. An Outlook label is neither match evidence nor a link gate; do not add it to Case search, match, association or receipt tables.
- **Automation is downstream of MAIL-13, not a catalogue caller.** AUTO-003 may later invoke the landed Core exact-message category action. It must pass the catalogue id through that use case and cannot list/update policy or call Graph directly.
- **A dedicated narrow administration surface is simpler than coupling concepts.** Add a sibling `/Administration/MailCategories` page/card using the existing administration conventions; leave `/Administration/Mailboxes` focused on mailbox allowlist and polling. This avoids reopening MAIL-002's address-only page model and avoids a generic “email rules” editor.
- **No new architecture boundary is required.** Core owns catalogue validation/authorization and the read policy consumed by MAIL-13; Infrastructure owns one EF table/store; Web is the admin caller. No ADR, top-level directory, runtime, generic settings framework, or Graph adapter belongs to MAIL-004.

## Recommendation

Proceed only because TICK-054 is a proven concrete caller. Implement a global Active/Disabled name allowlist in Pegasus with one dedicated admin page and no Graph synchronization. Land MAIL-004 before refreshing/executing MAIL-13. Do not implement search or linking integration. If MAIL-13 no longer includes category assignment before MAIL-004 is taken, close/archive MAIL-004 without code because administration-only dormant configuration would have no consumer.

## Acceptance direction

Core tests prove normalization, duplicates, authorization, version/replay and Active-only resolution. Integration/Web tests prove persistent history, no DELETE, inaccessible policy for non-Administrators, no Graph identifiers/colors, accessible add/disable flow, and the actual MAIL-13 read-policy seam. Local evidence performs no Outlook/Azure write.
