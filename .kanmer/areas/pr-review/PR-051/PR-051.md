## Why

The protected AssociationLeaseState records only Case id, receipt/Case versions, lease token, and association operation key. It does not bind the preparation to the exact retained message/receipt or to Link versus Unlink. A prepared confirmation can therefore be carried to another message targeting the same Case (or repurposed across action kinds) and the final handler will resolve that other message server-side and submit a new valid Core fingerprint.

## Required outcome

Bind the prepared authority to the exact server-derived message/receipt and the exact Link or Unlink intent, then reject any mismatch before mutation. Reuse the existing protected TempData and Core commands; add no new store or generic authorization framework.

## Verification

- [x] Prepare Link for message A and prove it cannot link message B to the same Case.
- [x] Prepare Unlink and prove its authority cannot be used for Link, and vice versa.
- [x] Exact same-message/same-action replay remains successful with one history entry.
- [x] The lease is safely resolved on rejected preparation-authority mismatch.
