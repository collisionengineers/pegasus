## What

Validate the Deleted Items Graph page envelope and next-link URI so every malformed successful response maps to the existing unavailable state.

## Why

At PR #469 head `eaf2f9f4eac577242ed301dd917f0682d4a77729`, `GraphMailClient.ReadFolderMessagesAsync` calls `root.GetProperty("value").EnumerateArray()` and constructs an absolute `Uri` from `@odata.nextLink` without translating missing/wrong-shaped `value` or an invalid URI. Those paths throw `KeyNotFoundException`, `InvalidOperationException`, or `UriFormatException`, none of which the Deleted boundary maps to `DeletedMailSearchState.Unavailable`; authenticated `/Inbox` therefore returns 500 for successful-but-malformed provider responses. This is the remaining shape case in [[PR-033]] and blocks [[TICK-053]].

## Verification

- Prove missing and non-array `value`, plus invalid/non-absolute next-link strings, return `DeletedMailSearchState.Unavailable`.
- Validate at the existing Graph-client boundary and translate malformed shape to the existing `InvalidDataException`; do not broaden the outer catch to swallow unrelated application errors.
- Preserve caller cancellation, exact mailbox/folder validation, GET-only access, and the existing fixed bounds.
