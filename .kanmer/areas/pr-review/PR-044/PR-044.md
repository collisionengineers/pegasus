## Why

At PR #477 head `83293162`, `OperationCanceledException` with the request token cancelled is rethrown both around the provider move and around provider-success completion. The durable row remains `pending`. PR-043 now correctly refuses every Pending replay and the filtered index blocks every different key, but there is no lease, worker, or later transition, so a client disconnect/cancel can strand the message permanently even when Graph may already have moved it.

## Verify

- Once a provider call has begun, preserve a durable recoverable state even if the request token is cancelled or persistence of the success result is interrupted.
- Use a bounded/internal persistence path that does not mistake request abandonment for permission to lose the external-operation outcome; do not add a worker, timer, lease, or blind retry unless genuinely necessary.
- Prove cancellation during provider execution and cancellation after provider success cannot leave an unrecoverable Pending row.
- Prove the later same-key status check probes only, resolves destination/source/unresolved outcomes safely, and different keys remain blocked until that recovery reaches a terminal result.
