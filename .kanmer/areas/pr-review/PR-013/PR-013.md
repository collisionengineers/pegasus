## What

Make an approved mailbox logical-folder refresh update the already tracked binding rows without creating two EF entities with the same `(ApprovedMailboxId, FolderType)` key.

## Why

PR #468 clears the loaded navigation collection and then adds new entities for every returned binding. A normal refresh that retains a logical type can leave the deleted tracked entity and a newly added entity with the same composite key in one change tracker, causing `SaveChanges` to fail instead of refreshing the mailbox configuration. This blocks [[TICK-064]].

## Verification

- Add a relational persistence test that saves an initial binding and refreshes the same logical type to a new exact folder identity.
- Prove unchanged, removed, and newly added logical types all save atomically without duplicate-key tracking failures.
- Preserve replay/version/audit behavior and the existing Web-only permission boundary.
