# Impact — SIMPLI-009

The files and modules this change touches, surveyed before planning.

## Current execution split

The repository currently has two materially different intake paths:

1. **Manual Web upload:** `UploadModel` calls `ProcessIntakeSubmission`, which stages the source through `ReceiveIntake.ExecuteInlineAsync`, creates or promotes the work item to an unleased `Dispatched` state, invokes `ProcessQueuedIntake` inside the Web request, then polls for evaluation and allocation completion.
2. **Queued sources:** `ReceiveIntake.ExecuteAsync` stages the work as `Pending`; the Worker timer claims and publishes it; the Worker queue trigger alone invokes `ProcessQueuedIntake`; poison and reconciliation functions handle exhausted delivery and expired leases.

The inline path is not merely a faster presentation path. It bypasses the durable dispatcher. `EfIntakeWorkStore.ClaimDispatchAsync` selects `Pending` and retry-scheduled work, while current recovery selects leased `Dispatching` or `Processing` work. An inline-created `Dispatched` row with no lease can therefore be stranded if Web stops after staging and before or during processing. This is a code/state-machine defect demonstrated with test data, not a live-data migration problem.

The transient simplification brief at `docs/temp-plans/simplify/simplify.md:1233-1241` identifies the intended scope: stage every source as pending, dispatch through the queue, make Worker the only `ProcessQueuedIntake` caller, remove Web inline processing and polling, repair historical unleased dispatched rows, and classify unexpected failures explicitly. That file is evidence for this survey, not a canonical requirement and not an owned edit for this ticket.

## Ripple effects

- Direct callers of `ProcessIntakeSubmission`, `ReceiveIntake.ExecuteInlineAsync`, and `IIntakeWorkStore.ReceiveForProcessingAsync` must be enumerated before contract removal.
- The Web response changes from “wait for processing and route to the result” to “acknowledge a durable receipt and expose status”; SIMPLI-008 is the adjacent owner for the staff-visible status surface.
- Queue delivery is at least once. The acceptance suite must prove duplicate delivery, enqueue-before-mark-dispatched races, dispatch lease expiry, processing lease expiry, crash after staging, poison replay, and idempotent allocation/triage side effects.
- No historical-row repair is required. Fresh tests must prove that staged work remains `Pending`, survives a crash after staging, and is later dispatched by Worker.
- Failure handling must distinguish expected terminal input/integrity failure, explicitly transient retry, exhausted retry/poison, and unexpected implementation failure. It must preserve queue-trigger failure signaling where Azure Functions redelivery is required.
- Web/Worker least privilege is part of the ownership claim: Web needs staging access; Worker needs queue receive/process and processor-owned persistence access.
- Local integration tests, actual Functions/Azurite tests, source composition proof, deployed settings, live trigger execution, SQL state movement, and rendered UI are separate evidence tiers.

## Out of scope

- Do not implement the SIMPLI-008 queued-status UI inside this ticket; depend on its settled receipt-keyed contract.
- Do not change mailbox polling, Sent evidence polling, external-work processing, Box custody behavior, report rendering, or case business policy merely because they share Worker infrastructure.
- Do not replace Azure Storage queues, change identifier-only payloads, introduce Service Bus, add a new runtime/deployment unit, or create another business-policy owner.
- Do not remove Web blob-staging permission or unrelated Box access.
- Do not rewrite accepted ADRs or treat the transient simplify plan as canonical truth.
- Do not edit applied historical migrations.
- Do not claim production activation from source/configuration alone, and do not perform any deployment, Azure setting, role, credential, or other cloud write without explicit approval for the exact target.
