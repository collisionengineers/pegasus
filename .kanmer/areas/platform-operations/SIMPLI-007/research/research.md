# Research — SIMPLI-007: the QDOS alpha acceptance gate in application composition

## Question

What is the "QDOS alpha acceptance gate", who calls it, what does it require, and what must be true to remove it from Core/Web composition while keeping the release validation it performs available in tooling?

## Findings (2026-08-17, read-only survey of `task/simpli-007-acceptance-gate` @ e6422250; dev has since moved to fc144848 in unrelated intake files)

- **It lives entirely in one Core file.** `src/Pegasus.Core/CoreAssembly.cs` holds the marker `public static class CoreAssembly;` (`:8`) and, below it, the whole gate: `QdosAlphaCapabilityEvidenceOutcome` `:10`, `QdosAlphaCapabilityObservation` `:16`, `QdosAlphaExternalGateEvidence` `:23`, `QdosAlphaAcceptanceRequest` `:29`, `QdosAlphaAcceptanceDecision` `:37`, `IQdosAlphaAcceptanceGate` `:42-45`, `QdosAlphaAcceptanceGate` `:52-316` with `AcceptanceManifestKind = "Pegasus.QdosAlpha.AcceptanceEvidence"` `:54`, 117 hard-coded capability IDs `:56-79`, `ExternallyCompletedCapabilityIds` (OPS-10/24/25) `:84`, `OfflineGateIds` `:87`, `ReleaseGateIds` `:93-104`, `Evaluate` `:112`.

Other tests carry the `QdosAlphaAcceptance` trait and must stay (the script's filter selects them): `RecoveryTests.cs:10,60,97,145,179,205`; `QdosTriageIntegrationTests.cs:22,71,101,132,182`; `QdosTriageReplayIntegrationTests.cs:10`; `QdosTriageCaseAssociationIntegrationTests.cs:12`. `ArchitectureTests`: no fact mentions the gate/runner/manifest; `DependencyDirectionTests` uses `typeof(CoreAssembly)` at `:44,:186,:225` — **the marker class must survive**. `Core.Tests`: zero references.

ADR-0013 (QDOS alpha implementation contract) mentions operator-acceptance gates generically (`:22,:62-65,:93`) but nothing about composition → **no ADR decided this; no supersession needed**. - **Dependency direction.** Core owns no manifest file paths or IO (those are in the test and the script), but does own two tooling concerns: the wire `kind` string and the release-requirement rosters. - **Pre-existing tooling staleness (out of scope, note only):** `Invoke-QdosAlphaAcceptance.ps1:505-514` hashes `OfflineAcceptanceTests.cs`, `LocalServiceSmokeTests.cs`, `NegativeMatrixTests.cs`, none of which exist under `tests/Pegasus.IntegrationTests` (only `RecoveryTests.cs` does), so `offlineMatrixSourceSha256` silently records one file.

## Implications

The gate is a release-validation checklist expressed as a Core singleton with no application caller — exactly what the ticket calls a "test-only manifest checker … part of the running application" that "carries obsolete release requirements". Removing it from Core and Web is deletion, not migration: the interface has no user, the registration has no consumer, and the only "caller" is a test that exists to prove the registration. The validation the tooling genuinely needs (manifest kind/schema, evidence hashes, dataset hash, source revision) is already performed by the PowerShell script; the one thing the C# gate adds is the capability-ID roster, which is stale (DOC-06) and duplicates `docs/capabilities.md`.

## Verified vs assumed

- Verified by grep/read: everything above with a `file:line`.
- Assumed (to confirm at plan time): the operator does not want the 117-ID roster preserved as an executable check in tooling; if they do, it belongs in the PowerShell script reading `docs/capabilities.md` rather than a Core singleton.
