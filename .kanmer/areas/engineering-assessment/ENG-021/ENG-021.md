## What

Seven findings from the review of [[TICK-077]] (PR #574), dispositioned as
deferred rather than fixed in that diff. All sit in the EVA **automatic**
submission path or around it. The three blockers found in the same review were
fixed before merge; these are what remains.

## Why

No Principal has automatic submission switched on, and Pegasus has never called
EVA in any environment, so none of these has ever been exercised. They should be
cleared **before any Principal turns automatic submission on**, because that is
the moment they stop being theoretical.

## The findings

1. **A delivered submission can be lost.** `EvaSubmissionStore` calls
   `RecordSubmissionAsync` with the caller's cancellation token, so a worker
   shutdown immediately after EVA accepted the instruction writes no
   `EvaSubmissions` row and no action history. The once-per-case guard then has
   no memory of the delivery and a later send creates a second claim.

2. **Lease expiry permits two concurrent submissions.** The processing lease is
   ten minutes and `ClaimProcessingAsync` will claim a `processing` row whose
   lease expired, while the submission record is written only *after* the EVA
   call. A slow Box read plus a large image upload is enough.

3. **The sweep swallows real database errors.** `EfAutomaticEvaSubmissionStore`
   catches every `DbUpdateException` and returns 0, so a denied permission or a
   constraint violation reports "enqueued none" forever rather than surfacing
   (rule 12). `EfVehicleWorkflowStore.IsDuplicateKeyFailure` is the existing
   convention and is not reused. Separately, all rows insert in one batch, so
   one conflicting row rolls back the whole pass.

4. **Unsynchronised token cache.** `EvaApiTransport.token` and
   `tokenExpiresAtUtc` are read outside the semaphore on the fast path and
   written inside it, so a reader can pair a fresh expiry with a stale token.
   The retry-once on 401 masks it, at the cost of re-uploading every image.

5. **Dead states.** `EvaSubmissionWorkState.Poisoned` and `.Pending` are never
   produced or consumed, and `RecordOutcomeAsync` explicitly rejects them.

6. **A generic message for a state refusal.** `CaseNotInReviewException` derives
   from `InvalidOperationException`, so a case that leaves Review between GET
   and POST of the Send page is shown the generic failure text rather than the
   state reason the other three domain refusals get.

7. **No consequence sentence on an irreversible action.** *Submit to EVA API*
   creates a claim FRD-07 says no API call can withdraw, and the control carries
   none. The design authority permits exactly one on a destructive action —
   whether to add it is the operator's decision, not a reviewer's, so it is
   asked here rather than written silently.
