## What

Four of the thirteen exported values are wrong or wrongly shaped. Fix them in
the mapping layer.

## Why

From `ap.QDOS26015`, against the three known-good samples (see [[CASE-019]] and
the sibling packaging ticket).

### Reference — carries our reference, should carry theirs

`reference/eva_information/eva_information.md:31-45` separates two EVA fields:
`Case/Po` is "our reference ... manually created by an admin worker"; `Claim no`
is "'Their' ref - ie the work providers reference". All three samples put the
provider's reference in the JSON `Reference` key — `1070277`, `SBL-B0492438`,
`AKH//47743/1`. We emit `ap.QDOS26015`.

It is hard-wired at `src/Pegasus.Infrastructure/Persistence/EvaHandoffStore.cs:870-874`
to `caseData.Identity.Reference`. Pegasus already captures the provider value as
**Claim number** (`CaseDataFieldNames.ClaimNumber`, extracted by
`QdosInstructionExtractionPolicy.cs:26-28` from `Claim Number` / `Our Ref` /
`Our Reference`, surfaced in reports as "Your reference"). The corpus test
`QdosMappingExtractionTests.cs:37-48` already pins the `AKH//47743/1` shape.

Operator decision (2026-08-24): emit the work provider's claim number.

### Inspection Address — must be a 6-line block

All three samples carry exactly 6 lines. Both reference samples use the
byte-identical literal `"Image-based Assessment\n\n\n\n\n"` — hyphen, lowercase
`b`, five trailing newlines. `Final Format Example 02` shows the same six slots
carrying a real address (`109 Valley View / Hoole / / / / CH490DJ`), so this is
addr1-addr5 plus postcode. We emit one line, `"Image Based Assessment"`.

### Vehicle Model — loses the make

`EvaHandoffStore.cs:881-885` prepends the make only on the staff-confirmed
vehicle-record branch (`Combine`, `:1055`); the case-field fallback reads
`Vehicle.Model` alone. Hence `X5 SE - X DRIVE Type 5 DOOR SUV` where the
predecessor had `BMW X5 XDRIVE30D AC AUTO`.

### Mileage Unit — casing

`EvaHandoffStore.cs:898-907` emits `miles` / `kilometres`; the samples use
`Miles` and `Km`. Low confidence EVA cares — see Open questions.

## Approach

- Swap the hard-wired `Reference` line for `FromCaseField(caseData.Claim.Number, ...)`,
  matching the twelve fields around it.
- Address: two blockers. The literal is defined twice and compared `Ordinal` —
  `src/Pegasus.Core/Address/Ext18InspectionAddressPolicy.cs:12` (written into the
  case) and `src/Pegasus.Core/Eva/CaseEvaMapping.cs:117` (what EVA must see).
  Change only the EVA-facing one; the case's own stored value is not EVA's
  business. And `CaseEvaMapping.NormalizeValue` (`:379`) calls `.Trim()`, which
  strips the padding. Add one `Format` helper in `CaseEvaMapping` producing
  exactly 6 lines, applied where the value is produced so JSON and provenance
  agree, plus a named documented exemption from the trailing trim for this one
  field. One place — this is the one-list-per-concept rail.
- Prepend the make on the Vehicle Model fallback branch too.

## Open questions

- [ ] **Mileage Unit casing and CRLF line endings.** The samples show `Miles`/`Km`
      and CRLF, but both look like Python-on-Windows artefacts of the predecessor
      rather than EVA requirements. Cheap to match if EVA is strict; otherwise
      leave the .NET defaults. An actual import would settle it.
- [ ] **Accident Circumstances.** The predecessor filled it from the letter's
      *Damage Area / Pre-existing Damage* block. Our `CircumstancesParagraph` rule
      (`QdosInstructionExtractionPolicy.cs:317-355`) deliberately terminates at
      `^(?:damage area|pre-existing damage|...)`, and this letter contains no
      "circumstances" text at all. Should damage-area text feed this key when no
      circumstances prose exists? Business rule, not a bug — may become its own
      ticket.
- [ ] **Instruction Date.** The QDOS letter writes a bare `Date:   13 August 2026`,
      absent from the label list (`QdosInstructionExtractionPolicy.cs:49-51`), so
      every QDOS case silently defaults to the receipt date. Adding a bare `Date`
      label risks matching the wrong date on other letter shapes. Likely its own
      INTK ticket rather than scope here.
- [ ] **VAT Status.** No extractor exists anywhere — staff-entry only, via the
      case workflow screen or MCP. The samples carry `No`. Confirm it is meant to
      be operator-entered rather than derived.
