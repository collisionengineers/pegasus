## What

Bring the exported field values into line with the JSON the original extractor
produces — the JSON EVA is known to accept.

## Why

From `ap.QDOS26015`, against three known-good samples and, since 2026-08-24,
against the **original extractor's source** (`CE Document Mapper V67`,
`app.py` + `providers.json`). See the `research` document for the verbatim
config and the quoted algorithms.

Operator instruction (2026-08-24): *"The json we output just needs to match the
original json and the way that works. Dont overthink. Dont add."* That is the
standard for this ticket — match, do not embellish.

## The changes

### a. `Reference` → the provider's own reference

Hard-wired at `src/Pegasus.Infrastructure/Persistence/EvaHandoffStore.cs:870-874`
to `caseData.Identity.Reference`. The original extracts it with `single_label` on
**`"Our Ref:"`** — the work provider's reference, `AKH//47743/1`. Pegasus already
captures this as **Claim number** (`CaseDataFieldNames.ClaimNumber`).

Swap the hard-wired line for `FromCaseField(caseData.Claim.Number, …)`, matching
the twelve fields around it.

### b. `Inspection Address` → the 6-line block

`app.py:2286` `normalise_inspection_address_value`, the author's own docstring:

> The output is always exactly 6 lines separated by 5 newlines … **Downstream
> JSON export feeds this to a management system that requires the 6-line shape;
> returning a bare empty string would fail the import.**

Rules, from the source:
- **always** exactly 6 lines: 1-5 body, 6 postcode. Unconditional — an empty
  address emits `"\n\n\n\n\n"`, so this is not a special case for image-based
  assessment.
- commas become line breaks before splitting
- surplus body lines join into line 5 with spaces
- postcode canonicalised to `OUTWARD INWARD`

The literal is `manual_input` **`"Image-based Assessment"`** — hyphen, lowercase
`b` — then normalised, giving `"Image-based Assessment\n\n\n\n\n"`.

Two blockers in our code:
- the literal is defined twice and compared `Ordinal`:
  `src/Pegasus.Core/Address/Ext18InspectionAddressPolicy.cs:12` (written into the
  case) and `src/Pegasus.Core/Eva/CaseEvaMapping.cs:117` (what EVA sees). Change
  only the EVA-facing one.
- `CaseEvaMapping.NormalizeValue` (`:379`) calls `.Trim()`, which strips the
  padding. Inspection Address needs a named, documented exemption.

### c. `Accident Circumstances` → label the damage area

Operator instruction (2026-08-24): *"include damage area with a line gap and
indicator of `Damage Area: `"*. Target shape:

```
<accident circumstances prose, if the document has any>

Damage Area: <damage area text>
```

Where the document carries no circumstances prose — the case for the QDOS audit
letters, confirmed by reading both PDFs of `ap.QDOS26015` — the value is just the
`Damage Area: …` part with no leading blank line.

**Assumption flagged for cheap correction:** blank line between, label exactly
`Damage Area: ` including the trailing space. No sample shows both parts
together, because every configured provider populates one or the other.

### d. `Mileage Unit` → `Miles` / `Km`

`app.py:158` — a **presence check**, not a unit conversion:
`{"positive_value": "Miles", "negative_value": "Km"}`. Pegasus emits lowercase
`"miles"` / `"kilometres"` (`EvaHandoffStore.cs:898-907`), matching neither.

### e. `Vehicle Model` — loses the make

`EvaHandoffStore.cs:881-885` prepends the make only on the staff-confirmed
vehicle-record branch (`Combine`, `:1055`); the case-field fallback reads
`Vehicle.Model` alone. Hence `X5 SE - X DRIVE Type 5 DOOR SUV` where the
predecessor had `BMW X5 XDRIVE30D AC AUTO`. Prepend the make on the fallback too.

### f. `Instruction Date` — accept the bare `Date:` label

Operator decision (2026-08-24): implement it.

The original uses `single_label` on the bare **`"Date:"`**. Ours
(`QdosInstructionExtractionPolicy.cs:49-51`) has only `Instruction Date` and
`Date of Instruction`, so **every QDOS case silently defaults to the receipt
date** via the fallback at `InstructionFieldExtraction.cs:43-59`.

Add `"Date"` to that label list.

**The regression risk, and the hook that prevents it.** The label regex
(`InstructionFieldExtraction.cs:157-168`) allows an optional colon and only
guards against a *preceding* word via `GuardedPrefixes`. A bare `Date` will
therefore also match the `Date of Accident:` row, yielding the value
`of Accident: 14/08/2026`. The existing `IsValidTyped` does **not** stop this —
it only runs during conflict resolution, and a lone bogus candidate is taken
unchecked at `:118`.

Use **`AcceptsValue`**, which filters at discovery (`:191`):

```csharp
new("Instruction date", ["Instruction Date", "Date of Instruction", "Date"],
    AcceptsValue: value => InstructionFieldEngine.ParseDate(value) is not null,
    IsValidTyped: value => InstructionFieldEngine.ParseDate(value) is not null,
    CanonicalValue: InstructionFieldEngine.CanonicalDate),
```

Both members are needed and they are not redundant: `AcceptsValue` gates
discovery, `IsValidTyped` gates conflict resolution.

**Must be covered by a test:** incident date still extracts correctly from a
letter carrying both `Date of Accident:` and a bare `Date:`. That is the
regression this change could cause.

### g. `Inspection Date` — the original report beats the instruction

Operator decision (2026-08-24): implement it.

Today the rule is the opposite. `ResolveConflictingCandidates`
(`InstructionFieldExtraction.cs:210-215`) documents itself as:

> among what remains the **earliest fragment** (document order — instruction
> material precedes appended reports) wins

So when the instruction letter and the appended engineer's report both carry an
inspection date, the instruction wins. The original extractor does the reverse:
`combine_instruction_and_engineer_report` (`app.py:3602`) takes the instruction
as the base and lets the report **override any field it filled**.

Scope this to `Inspection date` only — that is what was decided; do not
generalise the reversal to every field.

Add one per-field policy member to `FieldDefinition`
(`InstructionFieldExtraction.cs:13-20`) — it already carries `IsRequired`,
`AcceptsValue`, `IsValidTyped`, `CanonicalValue`, `GuardedPrefixes`, so a further
per-field policy knob follows the existing convention rather than inventing a
mechanism. Set it on `Inspection date`, and in `ResolveConflictingCandidates`
select `Max(FragmentRank)` instead of `Min` when it is set.

**Update the docstring at `:210-215`** — it currently states the earliest-wins
rule as unconditional, and would become false.

Note this changes nothing for `ap.QDOS26015`: the instruction letter carries no
inspection date there, so the report's date already wins by being the only
candidate. The change matters only when both documents carry one.

## Resolved — no change needed

**`VAT Status` blank is correct for QDOS.** A presence check whose config is
**empty** for QDOS; `resolve_presence_check` returns `""` for a blank config.
Blank by design, not by failure. Do not add an extractor, a default, or a staff
prompt.

**`Mileage` from the DVLA/DVSA lookup is intentional** (operator, 2026-08-24).
The original fills it only from an engineer's report `Speedo:` reading and emits
`""` otherwise; Pegasus fills it from the MOT lookup as a `suggested` value via
ENG-013. This divergence is deliberate and stays. Do not "restore parity" here.

## Not in scope

`ensure_ascii=False` — the original writes non-ASCII as literal UTF-8, never
`\uXXXX`, and Pegasus's default `JavaScriptEncoder` escapes it. Same serializer
options line as the indentation, so it went to [[ENG-014]].
