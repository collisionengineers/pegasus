## What

Bring the exported field values into line with the JSON the original extractor
produces — the JSON EVA is known to accept.

## Why

From `ap.QDOS26015`, against three known-good samples and, since 2026-08-24,
against the **original extractor's source** (`CE Document Mapper V67`,
`app.py` + `providers.json`). See the `research` document for the verbatim
config and the quoted algorithms. That source settles several questions that
were previously inference.

Operator instruction (2026-08-24): *"The json we output just needs to match the
original json and the way that works. Dont overthink. Dont add."* That is the
standard for this ticket — match, do not embellish.

## The changes

### a. `Reference` → the provider's own reference — **confirmed**

Hard-wired at `src/Pegasus.Infrastructure/Persistence/EvaHandoffStore.cs:870-874`
to `caseData.Identity.Reference`. The original extracts it with
`single_label` on **`"Our Ref:"`** — the work provider's reference,
`AKH//47743/1`. Pegasus already captures this as **Claim number**
(`CaseDataFieldNames.ClaimNumber`).

Swap the hard-wired line for `FromCaseField(caseData.Claim.Number, …)`, matching
the twelve fields around it.

### b. `Inspection Address` → the 6-line block — **now a stated requirement**

`app.py:2286` `normalise_inspection_address_value`, the author's own docstring:

> The output is always exactly 6 lines separated by 5 newlines … **Downstream
> JSON export feeds this to a management system that requires the 6-line shape;
> returning a bare empty string would fail the import.**

Rules, verbatim from the source:
- **always** exactly 6 lines: 1-5 body, 6 postcode. Unconditional — an empty
  address emits `"\n\n\n\n\n"`, so this is not a special case for
  image-based assessment.
- commas become line breaks before splitting (`re.sub(r"\s*,\s*", "\n", text)`)
- surplus body lines join into line 5 with spaces
- postcode canonicalised to `OUTWARD INWARD`

The literal is `manual_input` **`"Image-based Assessment"`** — hyphen, lowercase
`b` — then normalised, giving `"Image-based Assessment\n\n\n\n\n"`.

Two blockers in our code:
- the literal is defined twice and compared `Ordinal`:
  `src/Pegasus.Core/Address/Ext18InspectionAddressPolicy.cs:12` (written into the
  case) and `src/Pegasus.Core/Eva/CaseEvaMapping.cs:117` (what EVA sees). Change
  only the EVA-facing one — the case's own stored value is not EVA's business.
- `CaseEvaMapping.NormalizeValue` (`:379`) calls `.Trim()`, which strips the
  padding. Inspection Address needs a named, documented exemption.

### c. `Accident Circumstances` → label the damage area

Operator instruction (2026-08-24): *"include damage area with a line gap and
indicator of `Damage Area: `"*.

The original maps QDOS circumstances with `two_labels` `"Damage Area || TP
Vehicle"` — it takes the damage-area block **raw, unlabelled**. The operator
wants it labelled and separated. Target shape:

```
<accident circumstances prose, if the document has any>

Damage Area: <damage area text>
```

Where the document carries no circumstances prose — which is the case for the
QDOS audit letters, confirmed by reading both PDFs of `ap.QDOS26015` — the value
is just the `Damage Area: …` part with no leading blank line.

**Assumption flagged for cheap correction:** that a blank line separates the two
and the label is exactly `Damage Area: ` including the trailing space. No sample
shows both parts together, because every configured provider populates one or
the other, never both.

### d. `Mileage Unit` → Miles / Km

`app.py:158` — this is a **presence check**, not a unit conversion:
`{"positive_value": "Miles", "negative_value": "Km"}`. Pegasus emits lowercase
`"miles"` / `"kilometres"` (`EvaHandoffStore.cs:898-907`), matching neither.
Emit the Title-case pair.

### e. `Vehicle Model` — loses the make

`EvaHandoffStore.cs:881-885` prepends the make only on the staff-confirmed
vehicle-record branch (`Combine`, `:1055`); the case-field fallback reads
`Vehicle.Model` alone. Hence `X5 SE - X DRIVE Type 5 DOOR SUV` where the
predecessor had `BMW X5 XDRIVE30D AC AUTO`. Prepend the make on the fallback too.

## Resolved — no change needed

**`VAT Status` blank is correct for QDOS.** It is a presence check whose config
is **empty** for QDOS, and `resolve_presence_check` returns `""` for a blank
config. Every QDOS case has a blank VAT status by design. Do not add an
extractor, a default, or a staff prompt. This closes the earlier open question.

## Open questions

- [ ] **Mileage from the MOT lookup is a divergence.** The original fills
      `Mileage` only from an engineer's report (`Speedo:`); for a QDOS
      instruction with none, it emits `""`. Pegasus fills it from the DVLA/DVSA
      lookup as a `suggested` value — deliberately, via ENG-013, at operator
      request. So for `ap.QDOS26015` the original gives `""` and we give
      `208602`. Existing shipped behaviour an operator asked for, so **not for me
      to remove**; but it is a real difference from "match the original". Keep,
      or match?
- [ ] **`Instruction Date`** — the original uses `single_label` on the bare
      **`"Date:"`**. Pegasus's label list
      (`QdosInstructionExtractionPolicy.cs:49-51`) has only `Instruction Date`
      and `Date of Instruction`, so every QDOS case silently defaults to the
      receipt date. Adding a bare `Date` label risks matching the wrong date on
      other letter shapes. Own INTK ticket, or fold in here?

## Not in scope

`ensure_ascii=False` — the original writes non-ASCII as literal UTF-8, never
`\uXXXX`, and Pegasus's default `JavaScriptEncoder` escapes it. Same serializer
options line as the indentation, so it went to [[ENG-014]].

The **audit / engineer's-report merge** (instruction is base; the original
report overrides any non-empty field, supplying `Speedo:` mileage, the `Miles`
probe and the inspection date) is understood and documented in `research`, but
Pegasus has no engineer's-report intake route today. Not scoped here.
