## What

Make `EvaSubmissionOutcome.Unknown` terminal. Pegasus does not retry an EVA
submission over the API. An unknown outcome is surfaced on the case for a
human to check EVA and decide.

Operator decision, 2026-08-28: *"we don't retry via api for now."*

## Why

[[TICK-077]] shipped with `EvaSubmissionPolicy.IsRetryable(Unknown) == true`
and a five-step backoff ladder. The reasoning was that an unknown outcome is
the only one where the case might not have reached EVA, so retrying is less bad
than not retrying.

The recorded vendor traffic says otherwise. In the connector's eight-pair
reproduction run (`tests/testsubmits/1706/`), each pair submitted the same case
twice — once with an image (HTTP 500) and once without (HTTP 200). The
successes returned these File References:

```
61185, 61187, 61189, 61191, 61193, 61195, 61197, 61199
```

Every gap is exactly 2. Had only the eight successes created records they would
increment by 1. **The failed 500s each consumed a reference number**, so EVA
allocated a record and then failed. A 5xx is therefore not evidence that
nothing landed — it is evidence that something partially did.

That removes the justification for retrying. Splitting the cases:

| What happened | Landed? | Retry safe? |
| --- | --- | --- |
| 4xx — EVA validated and refused | No | Yes, but pointless: same payload, same refusal |
| 5xx — EVA allocated, then failed | Partially | **No** |
| No response — timeout, connection died | Unknown | No |

Nothing is both unsafe-to-leave and safe-to-retry. EVA offers no fetch, no
search and no idempotency key, so Pegasus cannot ask whether a claim arrived.
A retry is a coin flip between sending nothing and creating a second claim that
no API call can withdraw.

## Approach

- `EvaSubmissionPolicy.IsRetryable` returns false for every outcome. Consider
  removing it and `EvaSubmissionRetryPolicy` outright rather than leaving a
  policy that always says no — a gate that gates nothing should be deleted.
- `ProcessQueuedEvaSubmission` records an unknown outcome as terminal and
  schedules nothing.
- The case surface shows the unknown outcome plainly enough that an operator
  knows to check EVA before doing anything. Labels and values only.
- Keep the per-attempt operation keys from `31659613`: they are still needed so
  a queue message redelivered for the same attempt replays rather than submits.
- Amend FRD-07's outcome table, which currently says `Unknown` is *"retried,
  with backoff, to an attempt cap"*.
- Decide what an operator does after checking EVA. If the claim arrived there
  is currently no way to record that in Pegasus, so the case would keep
  offering Send to EVA — that gap needs closing or explicitly accepting.
